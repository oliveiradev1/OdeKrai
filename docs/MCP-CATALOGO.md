# Catálogo de servidores MCP públicos

Pesquisa realizada em 1º de novembro de 2026. O arquivo `src/core/mcp-service-catalog.json` contém somente dados apresentados pela interface: nome, fornecedor, página oficial de documentação (fonte), endpoint confirmado, transporte, autenticação documentada e disponibilidade no OdeKrai. `sourceCodeUrl` identifica o repositório oficial quando confirmado.

Todos os sete serviços têm servidor oficial confirmado; portanto, nenhum recebeu o status “sem servidor oficial confirmado”. “Não disponível” descreve uma limitação atual do cliente OdeKrai ou uma restrição documentada ao cliente, não a inexistência do servidor do fornecedor.

## Estado mostrado na interface

- **Disponível para configurar:** há endpoint oficial e método de autenticação compatível com o fluxo atual. A pessoa ainda precisa iniciar a configuração.
- **Configurado:** servidor salvo, mas a última chamada de teste não comprovou conexão.
- **Conectado:** o comando `mcp_test_connection` concluiu com sucesso e o runtime ainda informa o servidor ativo. Apenas salvar URL ou credencial nunca produz este estado.
- **Não disponível:** existe uma limitação de compatibilidade/restrição, descrita acima.

Nos cartões configuráveis, “Configurar” abre os campos de URL e autenticação. A configuração e o teste de conexão só acontecem após envio explícito desse formulário. Tokens são enviados ao Gerenciador de Credenciais pelo comando Rust já existente; o frontend os limpa após salvar. Não há instalação automática de pacote ou processo local.

## Evidências dos requisitos e ressalvas

- O GitHub documenta o endpoint remoto `https://api.githubcopilot.com/mcp/` e a autenticação PAT Bearer na página de configuração vinculada na tabela. A aba Pública fixa esse endereço no cartão e não permite substituí-lo. O link de criação abre a página oficial de [gerenciamento e criação de tokens pessoais fine-grained](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens); o botão do cartão aponta para o formulário oficial de criação `https://github.com/settings/personal-access-tokens/new`.
- A página oficial do GitHub diz que o servidor remoto usa OAuth de um clique por padrão. A página oficial de descoberta de autenticação afirma que esses metadados são “only published for MCP clients using RFC 9728 to discover the OAuth 2.0 endpoints”. Portanto, a descoberta segue a autorização MCP (recurso protegido RFC 9728 e metadados OAuth), e o cliente OdeKrai precisa estar cadastrado como GitHub App ou OAuth App. A documentação de descoberta está marcada como prévia pública. O guia oficial do servidor diz que o segredo do cliente é necessário na troca do código e recomenda um app dedicado para clientes distribuídos, pois o segredo pode ser conhecido pelo usuário do dispositivo. O client ID público fica vazio no repositório até o desenvolvedor registrar o app; o segredo é informado pelo usuário, armazenado só no Gerenciador de Credenciais e nunca distribuído pelo OdeKrai. Fontes: [descoberta de autenticação GitHub](https://docs.github.com/en/apps/github-authentication-discovery-endpoints), [integração de host do servidor MCP](https://github.com/github/github-mcp-server/blob/main/docs/host-integration.md), [fluxo OAuth documentado pelo servidor](https://github.com/github/github-mcp-server/blob/main/docs/oauth-login.md).
- A conexão OAuth solicita somente `read:user`, usado para mostrar o login devolvido pela API autenticada do GitHub. O transporte MCP envia `X-MCP-Readonly: true`, que filtra ferramentas do servidor para leitura. Antes do navegador, o cartão explica as permissões e orienta a conferir o consentimento. As fontes não enumeram um conjunto de escopos MCP de leitura que dê acesso privado a repositórios sem também conceder capacidades de escrita; portanto, o OdeKrai não solicita `repo` por padrão e dados de repositórios privados podem não ficar disponíveis. A API autenticada de usuário documenta `read:user` como escopo para a resposta privada; não se solicitam escopos de escrita.
- O botão **Desconectar** revoga a autorização GitHub pelo endpoint oficial `DELETE https://api.github.com/applications/{client_id}/grant`, usando o client ID e o segredo do app em autenticação Basic e enviando o access token no corpo. Se a API não confirmar, a interface informa que as credenciais locais foram removidas, mas que a revogação remota não foi confirmada. Para os demais servidores OAuth, é usado o endpoint de revogação anunciado nos metadados. Fontes: [revogar autorização de OAuth App](https://docs.github.com/en/rest/apps/oauth-applications#revoke-a-grant-for-an-oauth-app) e [excluir token de app](https://docs.github.com/en/rest/apps/oauth-applications#delete-an-app-token).

Trechos oficiais consultados:

- GitHub Docs: “one-click OAuth authentication by default” e o servidor só acessa os escopos aprovados no consentimento ([configuração do servidor MCP remoto](https://docs.github.com/en/copilot/how-tos/provide-context/use-mcp-in-your-ide/set-up-the-github-mcp-server)). A página [GitHub authentication discovery endpoints](https://docs.github.com/en/apps/github-authentication-discovery-endpoints) confirma que os metadados OAuth são publicados para clientes MCP via RFC 9728 e identifica a documentação como prévia pública. O guia do servidor documenta o cliente como GitHub App ou OAuth App e o segredo na troca do código.
- Repositório oficial `github/github-mcp-server`: cada host MCP precisa configurar GitHub App ou OAuth App; `X-MCP-Readonly` “Enables only read tools” ([guia do servidor remoto](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md)).
- GitHub REST: `/user` indica `read:user` para obter a resposta privada do usuário autenticado ([endpoint de usuário autenticado](https://docs.github.com/en/rest/users/users)). A revogação de autorização de OAuth App documentada pela API exige client ID e client secret ([revogação OAuth App](https://docs.github.com/en/rest/apps/oauth-applications#revoke-a-grant-for-an-oauth-app)).
- O GitHub recomenda tokens fine-grained e escolher somente os repositórios e permissões mínimos. Para uma base de leitura, o cartão sugere `Metadata: Read` (selecionada automaticamente), `Contents: Read`, `Issues: Read` e `Pull requests: Read`; os dois últimos dependem das ferramentas que a pessoa pretende usar. Escrita e outras permissões só devem ser adicionadas para as ferramentas correspondentes. Não existe uma lista universal de permissões para todos os usos: a documentação do GitHub MCP diz que o token deve ter os escopos necessários às ações desejadas, o guia de [filtragem de escopos do GitHub MCP](https://github.com/github/github-mcp-server/blob/main/docs/scope-filtering.md) relaciona permissões a toolsets, e a [referência oficial de permissões fine-grained](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens) detalha requisitos por endpoint.
- O cartão Figma não mostra botão Configurar nem Conectar enquanto o OdeKrai não estiver no catálogo autorizado. Ele mostra o endpoint, o login requerido, a restrição e um botão para abrir o guia oficial. A documentação diz que o servidor remoto usa `https://mcp.figma.com/mcp` e que a pessoa “sign in with your Figma account the first time you connect”. Ela não descreve o protocolo OAuth do fluxo, então esse detalhe permanece NÃO VERIFICADO.
- A documentação oficial do Google marca os servidores Gmail, Calendar e Sheets como **Developer Preview** e lista a participação no Google Workspace Developer Preview Program como pré-requisito. Ela exige um projeto Google Cloud, ativação das APIs de produto e MCP, tela de consentimento e cliente OAuth marcado para agente. Os endpoints são `https://gmailmcp.googleapis.com/mcp/v1`, `https://calendarmcp.googleapis.com/mcp/v1` e `https://sheetsmcp.googleapis.com/mcp/v1`, todos com Streamable HTTP.
- Os cartões Google mostram as etapas de configuração por serviço. O fluxo usa um consentimento por endpoint, escopos fixos calculados no Rust e não envia `include_granted_scopes`; cada endpoint armazena sua autorização separadamente no Gerenciador de Credenciais. Como o cliente Google configurado no app deve aceitar o retorno local, os cartões instruem cadastrar `http://127.0.0.1:43117/callback`; a documentação geral do Google para apps desktop confirma o padrão de loopback em IP e a validação do redirect URI. O client ID embutido ainda está vazio neste checkout, por isso o serviço não pode ser conectado até o cliente público ser configurado pelo distribuidor do OdeKrai. O segredo informado pelo usuário fica somente no Credential Manager.
- Escopos usados: Gmail `gmail.readonly` e `gmail.compose` (o guia oficial os lista como necessários ao Gmail MCP); Calendar `calendar.calendarlist.readonly`, `calendar.events.freebusy` e `calendar.events.readonly` (lista oficial do Calendar MCP); Sheets `spreadsheets.readonly` (escopo oficial de leitura aceito pelas ferramentas de leitura). A autorização adiciona `access_type=offline` e `prompt=consent`, conforme orientação do Google para receber refresh token e renovar consentimento; não usa autorização incremental.
- Gmail: a referência oficial MCP lista `create_draft`, ferramentas de leitura e ferramentas de rótulos, sem ferramenta de envio. O escopo `gmail.compose` também permite operações de envio na API Gmail; por isso o OdeKrai libera somente `create_draft` e ferramentas de leitura conhecidas, bloqueando rótulos, envio e nomes de ferramenta não reconhecidos. O envio continua indisponível; a pessoa pode revisar e enviar o rascunho dentro do Gmail.
- Quando um refresh Google retorna `401` ou `invalid_grant`, o erro orienta conectar novamente o serviço; o cartão oferece **Autorizar novamente com Google**. A conexão real e o comportamento do cliente OAuth ainda exigem validação no Windows com credenciais próprias e inscrição no programa.

Trechos oficiais consultados para Google Workspace (1º de novembro de 2026):

- Gmail, Calendar e Sheets declaram como pré-requisito: “Membership in the Google Workspace Developer Preview Program.” Os guias também exigem projeto Google Cloud, APIs de produto e MCP, consent screen e client ID. Fontes: [Gmail MCP](https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server), [Calendar MCP](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server), [Sheets MCP](https://developers.google.com/workspace/sheets/api/guides/configure-mcp-server).
- Os mesmos guias instruem o client a usar `access_type=offline` para receber refresh token e `prompt=consent` para obter um novo refresh token após consentimento anterior. A documentação desktop do Google descreve o callback loopback `http://127.0.0.1:<port>` e exige que o `redirect_uri` corresponda ao cadastrado no cliente OAuth: [OAuth 2.0 para apps desktop](https://developers.google.com/identity/protocols/oauth2/native-app).
- Gmail MCP lista `create_draft` e ferramentas de leitura; o exemplo oficial explica que o rascunho pode ser revisado e enviado no Gmail. A configuração pede `gmail.readonly` e `gmail.compose`: [referência de ferramentas Gmail MCP](https://developers.google.com/workspace/gmail/api/reference/mcp), [escopos Gmail MCP](https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server).
- Calendar MCP lista os três escopos `calendar.calendarlist.readonly`, `calendar.events.freebusy` e `calendar.events.readonly`: [escopos Calendar MCP](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server). Sheets oferece leitura com `spreadsheets.readonly`: [escopos da API Sheets](https://developers.google.com/workspace/sheets/api/scopes).
- `lovable.dev/mcp` é a página de apresentação, não o endpoint; a documentação operacional confirma `https://mcp.lovable.dev`. O guia da Lovable define cliente local como um programa executado no computador que conclui login em `localhost` ou `127.0.0.1`; diz que ele “registers with Lovable automatically” e não precisa de aprovação da Lovable. O callback do OdeKrai é `http://127.0.0.1:<porta>/callback`, então o OdeKrai entra nessa categoria. O cartão fica disponível para configuração OAuth, mas Conectar só é habilitado quando a consulta dos metadados confirma `registration_endpoint`; o fluxo real ainda depende de validação com a Lovable. Clientes hospedados ou sem conexão pré-configurada podem precisar de OAuth customizado. Fonte: [documentação MCP da Lovable](https://docs.lovable.dev/integrations/lovable-mcp-server).
- O Notion documenta o endpoint remoto, Streamable HTTP, OAuth 2.0 com PKCE e registro dinâmico de cliente. O guia instrui verificar `registration_endpoint` e registrar o cliente quando ele existir. Para o endpoint oficial do Notion, o cartão oferece somente OAuth; a documentação consultada não confirma uma autenticação alternativa por token pessoal/Bearer independente do OAuth. Um access token OAuth é enviado como Bearer no transporte, mas isso não constitui uma segunda opção de autenticação para a pessoa.

No cartão do Notion, a conexão verifica primeiro os metadados OAuth. Quando existe `registration_endpoint`, o OdeKrai registra o cliente automaticamente, usa o `client_id` retornado e o guarda junto da autorização no Gerenciador de Credenciais. Não há campo para informar um client ID manual no cartão Notion: o guia oficial não documenta essa alternativa para o serviço. Se o endpoint não anunciar registro dinâmico, a ação Conectar permanece bloqueada e a tela orienta a consultar o guia. Os escopos são opcionais e enviados apenas na autorização iniciada pela pessoa.

Trechos oficiais consultados para Lovable (1º de novembro de 2026):

- O guia confirma que o servidor MCP está em `https://mcp.lovable.dev` e distingue clientes que executam no computador e fazem callback em `localhost`/`127.0.0.1`; para esses, afirma que “It registers with Lovable automatically”. No cartão do GitHub, **Conectar com GitHub** usa `mcp_oauth_authorize`; o login vem do endpoint autenticado `/user`, é guardado junto à autorização no Gerenciador de Credenciais e nunca inclui access token na interface. **Usar token pessoal (avançado)** mantém o PAT no Gerenciador de Credenciais, sem leitura pelo frontend. Respostas HTTP 401 e 403 mostram uma mensagem fixa sem o corpo bruto da resposta.

## Comportamento e segurança

O catálogo não ativa ferramentas automaticamente. O teste apenas inicializa o servidor e obtém a lista de ferramentas; cada ferramenta MCP continua desativada por padrão e precisa ser ativada separadamente em Privacidade e permissões. O motor Rust mantém validação de schema, risco, aprovação e auditoria existentes. A resposta dos servidores segue sendo conteúdo externo não confiável.

Nenhuma conta real foi conectada durante esta pesquisa. A disponibilidade final depende do sucesso de uma tentativa iniciada pelo usuário no próprio OdeKrai.
