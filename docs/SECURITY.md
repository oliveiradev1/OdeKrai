# Segurança

## Loop de agente

Falhas do provedor são convertidas em categorias internas e mensagens seguras antes de chegar à interface ou ao `diagnostic.log`. A classificação distingue credencial negada (401/403), limite (429), modelo/endpoint ausente (404), solicitação/resposta inválida (400 ou payload inválido), transporte e indisponibilidade 5xx. Para OpenAI `gpt-6-luna`, o adaptador inclui `reasoning_effort: none` somente quando envia ferramentas, conforme a exigência publicada para function calling no Chat Completions. Os detalhes técnicos registram somente etapa e status conhecidos; corpo da resposta, conversa, credencial e request ID não são registrados. Quando uma ferramenta falha ou excede o tempo, o loop termina sem pedir ao modelo uma resposta final que possa aparentar sucesso.

`agent_run` é chamado pela tela de Conversas através de um canal Tauri. O loop usa as habilidades ativas do registro Rust, schemas fechados, limites por execução, truncamento e cancelamento. O modelo fornece somente nome e parâmetros; o Rust calcula risco, modo e decisão. A origem permanece `Model`; taint é estado separado mantido pelo Rust e força aprovação para efeitos colaterais após resultados de ferramentas.

O provedor principal e os fallbacks são armazenados com a conversa. O roteador exige credencial, adaptador compatível e tool calling verificado ou opt-in nativo. O failover só ocorre em falha transitória antes de qualquer saída observada; chamadas de ferramenta só são executadas após a resposta completa e não são repetidas pelo failover. O limite por execução inclui turnos, duração, tokens, quantidade de ferramentas e chamadas repetidas.

Chamadas e resultados técnicos são persistidos em `agent_messages` com tipo, habilidade, id de auditoria e hashes de parâmetros/resultados. Cartões separados persistem descrição segura, risco, decisão, status e resumo, sem argumentos ou resultados brutos. O canal Tauri envia `AgentEvent`; `agent_cancel` cancela uma conversa e o kill switch cancela todas. A interface apenas apresenta os dados do Rust e nunca decide permissões. Consulte [`TRACEABILITY.md`](TRACEABILITY.md).

Conteúdo lido de arquivos locais pode conter instruções maliciosas. A validação de caminhos, `.history` e `.trash` não remove esse risco. Resultados de habilidades são delimitados e rotulados como dados não confiáveis; taint continua ativo nas chamadas seguintes e a política Rust exige aprovação para efeitos colaterais.

- Provider keys are saved by the Tauri backend through `keyring` in Windows Credential Manager. The frontend holds typed text only while configuring the provider and cannot retrieve saved secrets.
- Chat calls Tauri commands; it does not send keys directly from the WebView. The web preview does not provide provider connectivity.
- The backend limits requests to known providers, HTTPS, provider-specific hosts, URLs without credentials or query parameters, no redirects, bounded message sizes, and bounded response times. Transport errors do not include key contents.
- The Rust backend validates the endpoint and path for the selected provider before storing or sending the credential. The catalog documents which providers offer model listing without generation. Errors shown to users are mapped by status; raw provider response bodies are neither displayed nor logged.
- The avatar is decoded in Rust only after validating PNG/JPEG/WebP magic bytes, a file size of at most 5 MiB, and bounded dimensions/pixel count. It is centered, reduced to 256 × 256, and re-encoded as PNG to remove metadata. The main window CSP allows `data:` in `img-src` to display the processed avatar.
- Sending prompts makes a real request to the selected provider and may incur costs. Check the provider's permissions, pricing, and retention policies.
- Vertex ADC/OAuth and AWS IAM/SigV4 are unavailable. Bedrock accepts only the API-key flow supported by AWS and described in the app.
- `keyring` still needs validation by running the updated app on Windows; unit tests do not prove persistence in the real Credential Manager.
- The production CSP does not allow the WebView to make network connections beyond local IPC; HTTPS provider requests run in Rust. Separate capabilities restrict auxiliary windows to events, while window, provider, and history commands check the caller window label in Rust.
- Links in model responses are rendered as controls without WebView navigation. Rust accepts only HTTP, HTTPS, and mailto, rejects credentials, backslashes, raw or encoded control characters, and private, loopback, or special IP literals, and opens approved links with the system browser. The first click per domain requires confirmation; remembered domains are editable in Settings.
- The local Agenda stores events in its own SQLite database. Google Calendar uses separate `google.calendar.*` tools for the primary calendar and scope `calendar.events.owned`. API results are untrusted data; create, update and delete require approval with event fields visible. OAuth refresh credentials stay in Windows Credential Manager and access tokens stay in memory. The API client uses HTTPS without redirects and maps errors without exposing response bodies.
- Local SQLite history contains plain-text messages. Disk and backup protection depend on Windows configuration; do not assume the app encrypts them.
- `ODEKRAI.md` is limited to 16 KiB, saved through an explicit user action, and included in the prompt only when its SHA-256 matches the approved version. Rust sends fixed rules first and rejects `system` messages from the frontend.
- Files in `memory/` are limited to 8 KiB and use simple names. Users can edit notes manually; the agent can create a new note only through the approved proposal flow described below. Up to 1,024 characters from `estilo.md` are included in the prompt. Do not store secrets: identity and memory are plain text. The agent has no command to write to `ODEKRAI.md` or `logs/`.
- Agent memory skills only list/search local notes or propose a new note. `memory.propose_note` always requires Rust approval and shows the exact text; the write uses create-new semantics and rejects recognized secret markers, valid CPF/CNPJ values, and valid payment-card numbers. This pattern-based filter is not exhaustive; memory remains plaintext and should not contain sensitive data. `memory.search` returns untrusted excerpts.
- `reminder.create`, `reminder.list`, and `reminder.cancel` use a local SQLite database. The Rust scheduler waits for the next due reminder and waits on a notification signal when none are pending; missed reminders are retried at startup. Windows notification delivery still requires validation in an installed build. Titles and notes are checked for recognized secret/document/card patterns before storage.
- `sheet.create_xlsx` and `sheet.read` execute only under the workspace/allowed-folder resolver. Read accepts CSV and XLSX with input/output bounds and at most 1,000 rows per sheet, and refuses results matching recognized secret/document/card patterns before returning them to the model. Spreadsheet creation blocks those patterns in cell/header content; formulas are restricted to a local-function/reference allowlist and are written but never evaluated by OdeKrai.
- Home path validation rejects UNC paths, drive roots, protected folders, `..`, reserved names, and links/junctions. OneDrive triggers a warning. Resistance to concurrent path replacement still needs native evaluation before future write tools.

## Phase 3 — policy, approval, audit, and halt

- `src-tauri/src/policy.rs` is a pure function implementing the mode × risk × origin × workspace matrix. The effective mode and per-tool exceptions come from `permissions.sqlite3`; the mode described in `ODEKRAI.md` is informational and does not control decisions.
- `src-tauri/src/security/skills.rs` registers typed Rust skills, closed schemas, Rust-calculated risk, previews, result trust, timeouts and rate limits. Skills begin disabled and only active skills are offered to the model. The Rust dispatcher blocks payments, protected system/browser/credential paths, identity/log/database locations, secret markers, invalid paths and anything outside the workspace or explicitly allowed folders.
- `screen.capture` é uma habilidade de Computador com risco Rust `captura_sensivel`, que sempre exige aprovação, inclusive em `Controle total` e quando a origem está contaminada. O Rust captura a área de trabalho virtual em memória, mostra uma prévia reduzida na janela nativa de aprovação e, somente depois da aprovação, salva o mesmo JPEG com nome simples na pasta de trabalho. A recusa descarta a captura em memória. A habilidade não inclui a imagem em pedidos ao provedor; análise e anexos de imagem não estão disponíveis no compositor.
- `web.fetch` aceita somente GET por HTTPS na porta 443, resolve e fixa IPs públicos em cada salto, desativa redirecionamentos automáticos e proxies e segue no máximo três redirecionamentos, apenas para domínios confiáveis. Limita respostas a 1 MB, aceita texto, HTML, JSON e XML, extrai Markdown limitado do HTML e identifica o resultado como dado não confiável. A primeira solicitação a cada domínio exige aprovação; os domínios aprovados compartilham a lista editável em Configurações → Links externos, armazenada no banco de permissões Rust.
- `mail.draft` is classified as external communication and always requires Rust approval, including in full control mode. Its approval preview contains the complete recipient, subject and body. Audit entries retain only parameter hashes and sizes. After approval, Rust opens a bounded, percent-encoded `mailto:` URL; oversized bodies are saved as a new `.txt` file in the workspace and the result tells the user where to attach it. The application never sends email.
- `discord.send` accepts only named webhook IDs registered in Settings. Rust calculates one Discord state for the catalog, tool offer, and system prompt: `not_configured`, `active` (configured and enabled), or `blocked` (configured and disabled). An absent webhook stops before any network request and the agent explains where to register one; the catalog never presents that state as active. When active, the tool is included in every agent-mode conversation, and each send still requires native approval in every permission mode, including `Controle total`. The webhook URL is validated against HTTPS `discord.com` or `discordapp.com` `/api/webhooks/{id}/{token}` URLs and stored only in Windows Credential Manager; the UI lists names and IDs without retrieving the URL. Rust disables redirects, sends a maximum of 2000 characters with empty `allowed_mentions`, blocks `@everyone`, `@here` and known secret markers, limits each webhook to one send every five seconds, and shows the exact text and registered name in the approval preview. HTTP errors omit the URL, token and response body.
- Revoking a Discord destination is confirmed by the native Windows dialog inside the Rust command before any DELETE request or local credential removal; canceling the dialog stops the operation.
- `workspace.read_file` lê arquivos de texto de até 64 KiB. `workspace.write_file` limita os arquivos a 1 MiB e guarda a versão anterior em `.history`. `workspace.delete_file` mantém seu comportamento atual usando `.trash`. As habilidades `files.write`, `files.append`, `files.mkdir`, `files.copy`, `files.move`, `files.rename`, `files.delete` e `files.apply_plan` usam a mesma lista de permissões e os mesmos bloqueios de caminho. Substituições preservam a versão anterior em `.history`; `files.delete` usa a operação da Shell do Windows com `FOF_ALLOWUNDO` e não tem alternativa de exclusão permanente. Lotes de movimentação mostram todos os itens em uma única aprovação, fazem validação prévia, têm limite de 50 itens e relatam falhas parciais. Essas habilidades operam em arquivos comuns e nunca os abrem nem executam.
- Pastas permitidas podem ter acesso somente para leitura ou para leitura e escrita; o workspace sempre permite leitura e escrita. Unidades de rede, traversal, pontos de nova análise, hard links, nomes reservados, caminhos longos demais no Windows e pastas protegidas são recusados. Leituras cuja raiz fica fora do workspace são marcadas como `Untrusted` e contaminam ações posteriores.
- `files.list`, `files.search` and `files.read` use the same Rust allowlist and fixed path blocks. Listing and search cap depth and result counts; text search also caps bytes read per file. `files.read` accepts UTF-8 or Windows-1252 text up to 64 KiB and refuses binary input. Results rooted in the workspace are marked local; results rooted in another allowed folder are untrusted and taint subsequent actions. These skills do not execute files.
- `system.open_url` aceita apenas HTTP e HTTPS, bloqueia IPs privados e de loopback e compartilha a lista editável de domínios externos, exigindo aprovação inicial por domínio. `system.open_path` e `system.reveal_in_folder` validam a pasta permitida e recusam extensões executáveis, de script, atalhos e documentos com macros; a primeira usa o aplicativo associado ao arquivo e a segunda apenas o Explorador. `settings.open` aceita páginas de uma enumeração fechada (`ms-settings:`), e `notification.show` usa o plugin oficial de notificações do Tauri. `app.launch` resolve somente identificadores cadastrados para executáveis `.exe` escolhidos em Aplicativos permitidos, exige aprovação em cada início e não aceita argumentos do modelo. As habilidades estão no registro Rust com risco calculado no backend e interruptor em Habilidades.
- `clipboard.write` e `clipboard.read` usam o plugin oficial de área de transferência do Tauri e sempre exigem aprovação. A leitura é limitada a 64 KiB, retorna conteúdo não confiável e mantém a execução contaminada para ações posteriores.
- `system.info` consulta Windows, memória, tempo ligado, bateria e espaço livre/total dos discos usados pelas pastas permitidas. O resultado usa rótulos genéricos e não inclui nomes ou caminhos de pastas, conta de usuário, rótulos ou identificadores de volumes.
- Approval requests use `ApprovalBroker` and open the `approval` window with a separate capability. Only that window can resolve a decision after Rust checks label, hash, expiry and one-time use. The loop waits for the oneshot and executes after approval. The queue accepts up to three pending requests and defaults to 120 seconds (configured from 30 to 600); closing the window denies the current request.
- Changing the global mode and enabling more permissive per-tool exceptions require confirmation in a native Windows dialog. `MessageBoxW` runs on a blocking worker (`spawn_blocking`); the async call awaits its result without occupying the UI thread. The default global shortcut is `Ctrl+Shift+F12`; conflicts are reported in settings. The kill switch persists the halted state, cancels registered requests/streams, denies pending approvals, and blocks new provider requests until explicitly resumed.
- Each decision and result is written to a daily JSONL file in `logs/`, with SHA-256 chaining and a confirmed write before execution. Audit verification or write failures block actions. Logs have no automatic retention or delete controls in the UI in this phase.

### Threats and limitations

- **Prompt injection and external content:** the policy keeps origin as Rust-side data; tainted actions above read risk require approval in every mode. Provider output and tool results cannot change the Rust mode, risk, or approval decision. `code.delegate` always requires approval, including in `Controle total`; its subprocess output and diff are untrusted, and its diff is never applied to the original project by this skill. The CLI runs with the user's Windows privileges and its worktree is not a security sandbox.
- **Approval forgery and parameter changes:** the response command validates the `approval` label, pending action ID, and hash; Rust recalculates the hash and revalidates paths immediately before execution. The UI never supplies the risk decision.
- **WebView XSS:** the approval window has a minimal capability and a local CSP without remote connections, and React renders the preview as plain text. A vulnerability executing code inside the approval window could still induce a click; approvals are never transferred to the main window.
- **TOCTOU:** canonicalization, reparse-point/hard-link detection, and validation immediately before the operation reduce destination replacement risks. A local process with the same privileges can still race changes during the operation; the implementation does not use immutable directory handles for the entire path walk.
- **Log tampering:** the chain detects changes and accidental breaks. It does not prevent edits and cannot resist malware or a local process able to rewrite files and recalculate hashes; it is not a signature protected by a key.
- **Approval flooding:** the queue is limited to three requests with one visible window at a time; excess requests are denied and audited.
- **General residual risk:** SQLite settings and logs are local files. A process running with the same user privileges can change them. This engine reduces agent mistakes/abuse and injection risks; it does not protect against local malware.

Google Calendar uses separate `google.calendar.*` tools and `calendar.events.owned` for the primary calendar. API results are tainted/untrusted data; create, update, and delete always ask for approval with the event fields visible. Credentials remain in Windows Credential Manager and access tokens in memory. Calls use HTTPS without redirects and map API errors without exposing response bodies.

The `npm run tauri:build` command checks assets and the `cfg(debug_assertions)` guard before packaging. See [`TRACEABILITY.md`](TRACEABILITY.md) for detailed requirements, implementation, tests, and status.
